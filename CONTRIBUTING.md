# Contributing to the VoiceLK TTS Bridge

Thanks for taking the time to help. The bridge is one part of VoiceLK, an academic
research project on Sinhala/English code-switched text-to-speech. It is small on
purpose: it turns text into WAV bytes and does nothing else. Please read the rules
below before opening a pull request — the first one catches most people out.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Where a change belongs

| You want to change… | Change it in… |
| --- | --- |
| The HTTP API, configuration, model loading, deployment files | This repository (`app/`, `deploy/`, `Dockerfile`, scripts) |
| Normalisation, G2P, the lexicon | The **research repository**, then sync |
| The Coqui `TTS` or `trainer` code | The **research repository**, then sync |
| Storage, authentication, audio records | The Spring Boot backend — the bridge holds no database or storage credentials |

### Never edit `vendor/` by hand

Everything under `vendor/` is generated by `tools/sync_from_ml.py` from the research
repository, which stays the source of truth: dataset preparation, training and
evaluation all use the same front-end code there. A hand edit here would make the
service feed a model phonemes it was never trained on, and it would be overwritten on
the next sync anyway.

To pick up a front-end change:

```bash
python tools/sync_from_ml.py --ml-root ../voicelk_ml          # refresh the copy
python tools/sync_from_ml.py --ml-root ../voicelk_ml --check  # confirm it is clean
```

Commit the refreshed `vendor/` tree together with `vendor/VENDOR_STAMP.json` in a
pull request of its own, and name the research-repository commit it came from.

### Keep it vendored

Libraries central to the model or the pipeline are shipped as source, not as pip
dependencies — the project must be presentable as a whole. Generic utilities (web
framework, numpy, torch) stay ordinary dependencies in `requirements.txt` or
`requirements-ml.txt`.

## Setting up

You need Python 3.11 and at least one trained run (its `config.json` plus a
checkpoint) under `models/` or wherever `VOICELK_MODELS_ROOT` points. Checkpoints are
never committed; see [`models/README.md`](models/README.md).

```bash
cp .env.example .env
./run_bridge.sh                  # Linux / macOS: builds a venv with CPU torch
```

```powershell
.\start_bridge.ps1 -Reload       # Windows: reuses the research training venv
```

Then check it end to end:

```bash
python smoke_test.py
```

`/health` should report the front-end status as `clean`. `drifted` means `vendor/`
no longer matches its stamp.

## Making a change

1. Open an issue first for anything beyond a small fix, so the approach can be
   agreed before you write it.
2. Branch from `main` (`fix/…`, `feat/…`, `docs/…`).
3. Match the surrounding code: type hints, module docstrings that explain *why*, and
   the existing error format (`status`, `error`, `detail`).
4. Run `python smoke_test.py` against a real checkpoint and listen to the clip. If you
   touched synthesis, try both model keys and a code-switched sentence.
5. Update `README.md` and `.env.example` when you add or change an endpoint, header or
   environment variable.
6. Keep commits focused and write messages in the imperative ("Add speaker validation").

## Pull requests

Fill in the template. A reviewer will ask about the following, so answer it up front:

- Which models and inputs you tested with.
- Whether the API contract changed — the Spring Boot backend depends on the paths,
  the response headers and the error codes.
- Whether any new setting needs a value on the server.

## Reporting problems

- **Bugs and mispronunciations:** use the issue templates. For a pronunciation
  problem, include the output of `POST /api/v1/phonemes` for the text — it shows
  whether the fault is in the front-end or the model.
- **Security issues:** do not open a public issue. Follow [`SECURITY.md`](SECURITY.md).
